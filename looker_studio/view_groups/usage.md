# 使い方・データの見方

View の比較ツールを**見る人**のための手引き。レポートを開いてから、何がどこに
出ていて、それをどう読めばよいかだけを書いてある。

- 導入の背景と効果 → `introduction.md`
- 作りと設定（作る人向け） → `README.md`

---

## 0. 3 行でいうと

- **base**（suffix を除いた View 名）ごとに 1 枚のカードが出る。
- カードは、その base に属する View を**ロジックが同じもの同士でグループに
  分けた**結果を見せている。
- **グループ数 = その base のロジックが何通りあるか。** 1 なら揃っている、
  2 以上なら差がある。

```
v_daily_sales_abjp … v_daily_sales_efuk （9 本）
        ↓ suffix を外して束ねる
  base = v_daily_sales
        ↓ ロジックでグループ化
  [abjp, abuk, abus]  [cdjp, cduk, cdus]  [efjp, efuk, efus]   ← 3 グループ
```

## 1. どこを見るか（2 つの画面）

| 画面 | 何を見るか | データソース |
|---|---|---|
| **カード** | base 1 つを深く見る。5 つのタブ | `viewlgc_t_diff` |
| **マトリクス** | 全 base を浅く見渡す。base × リージョン × suffix の表 | `viewlgc_vw_t_matrix` |

**探すときはマトリクス、読むときはカード。** マトリクスで「どの base が割れて
いるか・どこが欠けているか」を見つけ、その base をカードで開く、という順に
使うと早い。

### データはいつのものか

**1 日 1 回、まとめて作り直している。** 画面を開いた時点の `INFORMATION_SCHEMA`
を読んでいるわけではないので、**今日デプロイした View は明日のカードに出る。**

例外が 1 つある。**運用メモ（note タブのいちばん下）だけは、スプレッドシートを
直せばカードを作り直さなくても反映できる**（管理者が該当の処理を流し直す）。

履歴は持っていない。**常に最新の 1 世代だけ**で、「先週はどうだったか」は
残っていない。

---

## 2. カードの開き方

コントロール（プルダウン）が **2 つ**ある。どちらも単一選択。

| | フィールド | 何を選ぶか |
|---|---|---|
| 1 つ目 | `base` | **どの View 群を見るか** |
| 2 つ目 | `ref_label` | **どのグループを基準にするか** |

`base` を選ぶと、2 つ目にはその base のグループだけが並ぶ。

**`ref_label` は選ばなくてよい。** 何も選ばなければ、**いちばん View の多い
グループ**が自動で基準になる（レポート側でそう並べ替えてある）。多数派を
基準にしておけば少数派が右に出るので、「多数派に対して何が違うか」という
読み方になる。

**基準を変えると比較の向きが変わる。** 「A を基準にしたときの B との差」と
「B を基準にしたときの A との差」は、出る内容が変わりうる。片方だけ見て
判断しないこと。

> 基準が意味を持つのは**ロジック差分タブだけ**。カラム定義・参照関係・SQL は
> 全グループを並べるので、基準を変えても中身は変わらない。

---

## 3. カードの見出し（バッジ）

カードのいちばん上に、base 名と小さなバッジが並ぶ。**ここだけで「詳しく見る
必要があるか」がだいたい決まる。**

| バッジ | 色 | 意味 |
|---|---|---|
| `9 View` | 灰 | この base に属する View の数 |
| `1 グループ` | **緑** | 全 View のロジックが同一。揃っている |
| `3 グループ` | **黄** | ロジックが 3 通りある。中身を見る価値がある |
| `suffix 未認識` | 黄 | 命名規則から外れた View がこの base に居る（§6） |
| `ラベル不一致` | 黄 | View に付いた `labels` が base の中で揃っていない。値は note タブ |

**グループ数が 2 以上でも「異常」ではない。** 国や系統でデータの性質が違えば
ロジックも違って当然で、このツールは**差の有無を判定するのではなく、差を
人が見られる形に置く**ためのもの。妥当かどうかを決めるのは人。

---

## 4. タブごとの読み方

タブは左から **note / カラム定義 / 参照関係 / ロジック差分 / SQL** の 5 枚。
どれも同じ 1 枚のカードの中なので、コントロールの選択はすべてのタブに効く。

### 4-1. note — 説明と運用メモ

出どころの違う 4 つを、箱を分けて縦に積んでいる（上から順）。

| 段 | 何が出るか | 変わるとき |
|---|---|---|
| **ラベル** | View に付いた `labels`（key:value） | View をデプロイしたとき |
| **View のリージョン** | location ごとの View 数と suffix の表 | View を別リージョンに増やしたとき |
| **View の description** | View 自身に付けた説明 | View をデプロイしたとき |
| **メモ** | 運用メモ（スプレッドシート） | 書き換えたその場で |

**中身が無い段は出ない。** ラベルを付けていない、description を書いていない、
という base では、その段ごと表示されない（「未設定」とだけ書いた行が毎回出ても
読む手掛かりにならないため）。**メモの段だけは常に出る**（未登録なら「未登録」）。

> 例外が 1 つ。「View の description を取得できませんでした」と出たときは
> **未設定ではなく取得の失敗**。黙って消すと気づけないので、これだけは
> 案内を出している。管理者に伝えてほしい。

「View のリージョン」の表はこう出る。**リージョンが 1 つでも出す**（どこに
置いてあるかは毎回知りたいことなので、割れているときだけの警告ではない）。

```
View のリージョン
  asia-northeast1  6  abjp, abuk, abus, cdjp, cduk, cdus
  asia-southeast1  3  efjp, efuk, efus
```

**description が base の中で割れていたら、割れた数だけタブになる。** 同じ
ロジックの View なのに説明が違えば、それ自体が情報なので黙って 1 つに
まとめない。

> **メモは人が書く場所。** 背景・経緯・運用上の注意など、機械が持っていない
> ことを残す。書き方は Markdown。

### 4-2. カラム定義 — 出力列の突き合わせ

**1 行 = 1 列名**の表。セルには**型**と、その右に小さく**モード**
（`NULLABLE` / `REQUIRED` / `REPEATED`）が出る。

> **列はロジック グループではない。** ここは**カラム定義（列名・型・モード・
> 説明）が同じ View 同士**で束ね直している。**だからロジック差分タブと
> 列の本数は合わない。** 表の上にもそう書いてある。

**このタブの値打ちは、ロジック差分に出てこない差が出ること。** SQL が完全に
同じでも、参照先テーブルの型が違えば出力列の型は違う（`amount` が jp は
`NUMERIC`、us は `FLOAT64` など）。**SQL が同一だから、差分タブには絶対に
出ない。** ここで**列が 2 本以上に割れていたら、それ自体が差**。

| 見た目 | 意味 |
|---|---|
| **地色（緑）** | **その行でいちばん多い内容と違う**（型 / NULL 制約 / 説明） |
| **枠（黄）＋ `⚠`** | **束の中で列の並び順が食い違う**、または**この列を持たない View がいる**。カーソルを乗せると `abus = #4 FLOAT64 NULLABLE` のように suffix ごとの内訳が出る |
| **`—`（灰）** | その束にこの列が無い |

**緑に「基準」は無い。** 多数派と違うセルに色が付くだけで、ロジック差分の
`ref_label` はこの表には効かない。

**表の上の案内文をまず読む。** 「カラム定義が 2 種類あります」「揃っていない列が
3 件あります」のように、どこを見ればよいかが先に出る。全 View で一致していれば
「N 本の View すべてでカラム定義が一致しています」と出るので、その base の
このタブは読み飛ばしてよい。

列名の行はスクロールしても残る。並び順（`ordinal`）は列どうしの差としては
扱わない（列を 1 本足すと以降がまとめてずれて、本当に見たい型の差が埋もれる
ため）。束の**中**での順序の食い違いだけ `⚠` の内訳に出る。

**論理名（description）は、書く運用を始めるまで空欄。** カラムの description に
`{"ja": "受注日", "en": "order date"}` のような JSON を書けば、日本語・英語の
論理名として表に出る。

### 4-3. 参照関係 — どこから読んでいるか

`FROM` / `JOIN` から起こした図。**参照関係の括りごとに 1 枚を縦に積む**
（タブではないので、切り替えずに一望できる）。

| 読み方 | |
|---|---|
| **矢印** | 「読んで作る」向き |
| **注記** | JOIN の種別と結合キー。**省略しない**（全部出す。図が縦横に伸びる） |
| **箱の色** | 凡例のとおり: 実テーブル / CTE / 最終 SELECT |
| **点線** | サブクエリ経由の参照 |
| **`*` で終わる名前** | View ごとに名前が違う箇所。共通部分だけを出して残りを `*` にしている（`orders_ab*`）。**箱にカーソルを乗せると実際の対応が出る** |

**カーディナリティ（1 対 N など）と主キーは描いていない。** SQL からは
分からないため。ここに出るのは「何を読んで何を作っているか」だけ。

> **ここでの括りはロジック差分とは別。** 参照名の base 部分（suffix を除いた
> 実体名）が同じものは 1 枚にまとめている。**ロジックは違っても、読んでいる
> ものは同じ**という場合が多く、図を 3 枚並べても同じ絵が 3 つ出るだけなので。
> まとめたときは図の上に「ロジックは 3 グループに割れていますが、参照関係は
> 2 通りです」と出る。

### 4-4. ロジック差分 — SQL の差だけを見る

**タブの枚数がそのままグループ数**になる。

```
[ 基準 abjp, abuk, abus 3 ][ cdjp, cduk, cdus 3 ][ efjp, efuk, efus 3 ]
   ↑ 常に選択（左ペイン）      ↑ ここだけ切り替わる（右ペイン）
```

- **先頭は基準のタブで、押しても切り替わらない。** 基準は左ペインに出しっぱなし。
- **色が対応している。** 基準タブと左ペインが薄い赤、選択中の比較タブと右ペインが
  薄い緑。押した先の色がそのまま下のペインに出る。
- **1 グループのときは 1 ペインだけ。** 同じ SQL を左右に並べても読むものが
  無いので、比較の色分けも付かない。

#### `{{P1}}` は何か

**グループ内の差は消してある。** `mart_abjp.orders_abjp` と
`mart_abus.orders_abus` のような suffix 違いは、同じロジックの中では
ノイズでしかないので `{{P1}}` のようなパラメータに置き換えている。
**だから左右に残るのは、ロジックの差だけ。**

**`{{P1}}` にカーソルを乗せると、種別と suffix ごとの実際の値が吹き出しで出る。**
末尾まで目を往復させずに済む。

#### 末尾の 2 つの折りたたみ

| 見出し | 中身 |
|---|---|
| **パラメータ化した箇所** | 何をノイズ扱いにしたかの全一覧。**判定の当否を人が確かめるためのもの**。種別（実体名 / 値（文字列） / 値（数値））も出る |
| **なぜ別グループになったか** | 割れている base でだけ出る。基準と比べて**最初に食い違った場所**とその理由 |

「なぜ別グループになったか」は、**想定より細かく割れたときにまず開く場所**。
理由が「値の違い」なら設定の問題（既定では値の差はパラメータ化して同じ
グループにする）、そうでなければ本物のロジック差、という切り分けができる。

> **判定の根拠は SQL のテキスト。** 実行結果が同じかどうかは見ていない。
> 逆に、結果が同じでも書き方が違えば差として出る。

### 4-5. SQL — 素のテキスト

`INFORMATION_SCHEMA` が持っている View の定義を**そのまま**出す。差分も等価
判定も通していない。

**ロジック差分では代わりにならない。** あちらはパラメータ化済みの SQL で、
実体名や値は `{{Pn}}` に置き換わっているし、**グループの代表 1 本ぶんしか
出ていない**。「この View に実際に何が書いてあるか」を読みたいときはこちら。

- **タブはグループではなく View（suffix）単位。** base の View が 1 本残らず
  並ぶ。探しているのは「abjp の SQL」であって「グループ 2 の SQL」ではないため。
- **リージョンごとの行に分かれている。** 並びはリージョン → suffix の文字数 →
  アルファベット順。
- どのグループに属しているかは、パネルの見出しに出る。

## 5. マトリクスの読み方

**行に base、列にリージョンと suffix を 2 段**に置いたピボット。
1 行 = 1 View なので、**1 セル = 1 View**。

```
                    asia-northeast1          asia-southeast1
                abjp  abuk  abus  cdjp     efjp  efuk  efus
v_daily_sales     1     1     1     2        3     3     3
v_summary         1     1     1     1        1           1    ← efuk が無い
v_pricing         1     2     1     1        1     1     1    ← abuk だけ別ロジック
```

| 見るもの | 意味 |
|---|---|
| **空白のセル** | **その環境にその View が無い。** 作り忘れか、意図的に作っていないか |
| **同じ行で数字が割れている** | **そこがロジック差分。** `1` が多数派（いちばん View の多いグループ） |
| **行全部が `1`** | その base は全環境で同じロジック |

数字は**ロジック グループの番号**（`group_no`）で、**1 がいちばん View の多い
グループ**。番号そのものに意味はなく、**同じ行の中で割れているかどうか**だけを
見る。

気になる base を見つけたら、カードのページで `base` にその名前を選んで開く。

> 番号ではなく有無だけを見たいなら、指標を `view_name` の COUNT にすると
> 「1 か空白」の表になる。差分のある base だけに絞るなら、フィルタに
> `has_multiple = true` を足す。

### マトリクスの列

| 列 | 中身 |
|---|---|
| `base` | suffix を除いた View 名 |
| `location` | BigQuery のリージョン（`asia-northeast1` など） |
| `suffix` | View 名の末尾。認識できなかったものは `(suffix なし)` |
| `view_name` | View 名そのもの |
| `group_no` | ロジック グループの番号（1 が最多グループ） |
| `group_label` | そのグループの suffix 列記（`abjp, abuk, abus`） |
| `group_size` | そのグループの View 数 |
| `view_count` / `group_count` / `has_multiple` / `unmatched_count` | base ごとの値。絞り込みに使う |

> **BigQuery で直に問い合わせるなら**、カードのテーブル（`viewlgc_t_diff`）
> にも同じ材料が `suffixes` / `locations` / `view_names` の 3 本の配列で
> 入っている（**添字が対応する**。`locations[i]` が `suffixes[i]` の View の
> リージョン）。ただし**配列は Looker Studio からは読めない**ので、
> レポートで使うならこのマトリクスのほうを読む。

## 6. よくある読み違い

**「グループが 2 つある＝バグ」ではない。**
差があること自体は普通にある。このツールがするのは、**差に気づける状態に
すること**まで。意図した差か直し忘れかを決めるのは人。

**「1 グループだから全部同じ」ではない。**
ロジックが同じでも、**出力列の型は違いうる**（参照先の型が違う場合）。
1 グループのカードでも**カラム定義タブは見る価値がある**。`⚠` が付いていたら、
SQL は同じなのに型が揃っていないということ。

**`suffix 未認識` のバッジ。**
命名規則から外れていて suffix を切り出せなかった View。**除外せず、単独の
base として並べている**（出さないと画面から消えてしまい、規則から外れた View
ほど気づけなくなるため）。1 View / 1 グループのカードになる。

**値（リテラル）の差は、既定ではロジック差にしない。**
`status = 'A'` と `status = 'B'` は同じグループになり、「パラメータ化した箇所」の
一覧に**値（文字列）**として出る。値の差も割りたい場合は設定で変えられる
（管理者に相談）。

**マトリクスの数字を足し算しない。**
`group_no` は番号であって量ではない。合計や平均に意味は無い。

## 7. 困ったとき

| 症状 | 見るところ |
|---|---|
| カードの上に「このカードには新しい CSS（世代 N）が要ります」と出る | **表示が崩れている合図。** テンプレートの CSS が古い。管理者に貼り直しを依頼する（内容自体は正しい） |
| 今日デプロイした View が出ない | 生成は 1 日 1 回。**明日のカードに出る**（§1） |
| メモを直したのに反映されない | メモだけは即時反映できるが、**反映の処理を流す必要がある**。待てるなら翌日の生成でも同じ結果になる |
| 「View が多いため先頭 128 件のみタブ表示しています（全 N 件）」と出る | 表示枚数の上限。**黙って消してはいない**ので、全体の件数はその案内で分かる。グループ側・基準側にも同じ形の案内がある |
| base のプルダウンに出てこない | 対象データセット / View 名の絞り込みから外れている可能性。管理者に確認 |
| 論理名（description）が空 | View / カラムに description を書く運用を始めていないため。書けば出る |

## 8. 用語

| 語 | 意味 |
|---|---|
| **base** | View 名から suffix を除いた部分。カード 1 枚の単位。`v_daily_sales_abjp` → `v_daily_sales` |
| **suffix** | View 名の末尾に付く環境・系統の識別子。`abjp` / `txus` など |
| **グループ** | **SQL のロジックが同じ View の束。** グループ数がその base のロジックの通り数 |
| **基準（`ref_label`）** | ロジック差分タブで左ペインに固定するグループ。比較の向きを決める |
| **パラメータ（`{{Pn}}`）** | グループ内の差を消すために置き換えた箇所。ほとんどは suffix 違い |
| **α 等価** | 「違っている箇所が一貫した 1 対 1 対応になっていれば同じロジック」という判定のしかた |
| **location** | BigQuery のリージョン。`asia-northeast1` など |
| **`snapshot_date`** | そのカードを作った日。履歴は持たないので常に最新の 1 世代だけ |
