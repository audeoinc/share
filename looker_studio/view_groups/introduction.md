# suffix 違い View の比較ツール — 導入の提案

> View ごとに人が書いているドキュメントを、**BigQuery がすでに持っている
> メタデータから自動で作ります。** あわせて **ロジックが何通りあるか**と
> **どこがどう違うか**まで整理するので、**起こり得ない差が起きたときに
> 気づけます。**

---

## 1. いま起きていること

私たちは同じ意味の View を suffix 違いで何本も持っています。

```
v_daily_sales_abjp   v_daily_sales_abuk   v_daily_sales_abus
v_daily_sales_cdjp   v_daily_sales_cduk   v_daily_sales_cdus
v_daily_sales_efjp   v_daily_sales_efuk   v_daily_sales_efus
```

### (1) View を増やすたび、ほぼ同じ内容のドキュメントを書いている

いま、View ごとの説明ページを Confluence に作っています。**View を増やすたびに、
ほぼ同じ内容を書きます。** しかもその大半は、列名・型・参照先・SQL 本体といった、
**BigQuery がメタデータとしてすでに持っているもの**です。
すでにある情報を、あらためて人が書き写す形になっています。

**ほぼ同じ内容が続くぶん、小さな違いの記載は漏れやすくなります。** 前の View の
ページを土台にして直す書き方になるので、実際に違っている数行だけが残ってしまう
ことがあります。どれだけ丁寧に書いても、**人が書く以上すべての差異を漏れなく
記載するのは難しい**性質の作業です。

その結果、ドキュメントと実物が少しずつ離れていくことがあります。
書いた人の問題ではなく、この作業のかたちから生まれるものです。

### (2) 確認はできる。ただし探す手間と加工する手間がかかる

差異を確認したいとき、見るものは 3 か所あります。

| 見るもの | そこにあるもの |
|---|---|
| Confluence | View の説明。人が書いたもの |
| Git | SQL の変更履歴 |
| BigQuery | 実際に動いている定義とカラム情報 |

**どれを見ても分かります。分からないのではなく、時間がかかるということです。**

- **探す手間（横断のとき）** — リンクは Confluence にまとまっているので、
  特定の View のページを開くこと自体は難しくありません。手間なのは
  **複数のページを跨いで情報を集めなければならないとき**です。
  9 本ぶんを行き来して、頭の中で突き合わせることになります。
- **加工する手間** — 差異を確認するツールはありますが、**一度に比べられる数が
  限られています。** そのうえ比較するにはダウンロードが要り、比較結果をもとに
  資料を作る手間も別にかかります。
- **代表だけを見るので、抜け漏れが起こりうる** — 同じ base の View を全部
  比較するのは現実的ではないので、**代表的なものだけを比べています。**
  合理的なやり方ですが、**比べた範囲の外に差があった場合は見えません。**


### (3) その結果、意図しない差に気づけないことがある

横展開はコピーで行うので、作った直後は同じでも時間が経つと差が生まれます。
**意図した差もあれば、意図しない差もあります。** 困るのは後者です。

| 起きること | なぜ気づけないか |
|---|---|
| 1 本だけ直して残りを直し忘れた | 直した本人しか知らない。エラーは出ない |
| 参照先テーブルの型が違って、出力列の型が変わった | **SQL は 1 文字も違わない**。差分を取っても出てこない |
| description（論理名）が片方にしか付いていない | 誰も見ていない |
| 廃止した CTE が 1 本にだけ残っている | 動くので気づかない |

**共通するのは「エラーにならない」こと。** 探して見比べない限り表に出てこないので、
**気づけるかどうかが、そのとき見た範囲に左右されます。**

## 2. このツールがすること

`INFORMATION_SCHEMA` から View の定義とカラム情報を毎日読み、base ごとに 1 枚の
カードを作って Looker Studio に出します。

```
9 本の View
   ↓  suffix を外して base 名で束ねる
v_daily_sales
   ↓  SQL ロジックが同じもの同士でグループ化
[abjp, abuk, abus]  [cdjp, cduk, cdus]  [efjp, efuk, efus]
   ↓
カード 1 枚（5 つのタブ）
```

### カードの中身

| タブ | 何が見えるか |
|---|---|
| **note** | View 自身の description と、運用メモ（description は新しく運用を決める必要あり → 6 章） |
| **カラム定義** | 列名・型・モード・説明を横に並べた表。**定義が違えば列が分かれる**（説明の部分は同上） |
| **参照関係** | どの実テーブルから、どの CTE を経て結果を作っているかの図 |
| **ロジック差分** | グループ間の SQL 差分。**suffix 違いはノイズとして消えている**（何をノイズ扱いにしたかは末尾に一覧で出る） |
| **SQL** | View ごとの素の SQL（View を選ぶタブつき） |

### グループ数が「差の有無」を一目で示す

**グループ数は、その base のロジックが何通りあるかを表します。**
1 なら全 suffix が同一。2 以上ならロジックに差があります。

**差があること自体は問題ではありません。** データの性質上、国や系統によって
処理を変える必要があるのは当然あります。**問題は、差があるという事実に
気づきにくいことです。** いまは、気づくためにその都度 SQL を
読み比べる必要があります。

このツールがするのは、**その差を認識できる状態にする**ことです。
グループ数で差の有無が分かり、差分タブで中身が読めるので、
「これは意図した差」「これは直し忘れ」という判断に進めます。
妥当かどうかを決めるのは人です。

## 3. 効果

**一言でいえば、起こり得ない差が発生したときに気づきやすい情報を出せることです。**

差の有無を機械が判定して警告するのではありません。**人が判断できる材料を、
判断できる形で毎日そろえておく**、という性格のツールです。

### 作る手間がなくなる — View ごとのドキュメントを書かなくてよくなる

View を増やすたびに書いていた説明の大半は、BigQuery がすでに持っている情報です。
**列名・型・モード・参照関係・SQL 本体は、いま何もしなくてもそのまま出ます。**
カード 1 枚にまとまるので、同じ内容を人が転記する必要がなくなります。
しかも実物から毎日作り直すので、**追いついていない**という状態になりません。

**論理名（description）だけは別です。** いま View にもカラムにも description を
書く運用がないので、そこは空のまま出ます。書けば出ますが、**書く運用を新しく
決める必要があります**（6 章）。

人にしか書けないこと（背景・経緯・運用上の注意）は、運用メモに残せば足ります。

### 変更したとき — その差分が妥当かを確認できる

1 本直せば、他との間に差が生まれます。いま知りたいのは
「差があるかどうか」ではなく、**その差が意図したものか、想定していないものか**です。

差分タブは suffix 違いを消したうえで残った差だけを出すので、
**ダウンロードも、資料化も要りません。**

そしてもう一つ大きいのは、**代表 2 本ではなく、その base の全 View が
毎日グループに分かれて出る**ことです。比較の数に上限がないので、
**「比べなかったから分からない」がなくなります。**

### 性質が違うとき — どういう差が存在するのかを把握できる

国や系統でデータの性質が違えば、ロジックも違って当然です。
ただ、**その違いが具体的に何なのか**を一覧できる形にはなっていません。

グループ数でいくつのパターンがあるかが分かり、差分タブでそれぞれが
どこでどう分かれているかを読めます。**現状の対応パターンの棚卸し**になります。

### 把握できると、要件への対応パターンを設計できる

ここがいちばん先につながるところです。既存の差がどんな種類なのか分かれば、
**新しい要件をどのパターンに乗せるか**を決められます。

- この差は 3 通りある。統一できるのはここまでで、ここから先は分けるしかない
- 今回の要件は既存のパターン B と同じ形なので、同じ作りにする
- この分岐はもう要らない。1 本に寄せられる

こういう議論を、**実物を見ながら**できるようになります。
いまは詳しい人の知識に頼っている部分を、誰でも同じものを見て話せるようにします。

### そのほか（副次的なもの）

| 見られるもの | 意味 |
|---|---|
| カラム定義の突き合わせ | **SQL が同一でも参照先の型が違えば出力列の型が違う。**差分には絶対に出ない情報 |
| 参照関係の図 | どの実テーブルから、どの CTE を経て作っているか |
| 論理名（description） | JSON から取り出してカラム定義に表示。**書く運用はこれから決める**（6 章） |
| 運用メモ | スプレッドシートに書けば note タブに出る。属人的な知識を残せる |

base × suffix で何が揃っていて何が無いかも見えるので、**View の棚卸しの土台**にもなります。

## 4. 仕組み — 「同じロジック」をどう判定しているか

ここがこのツールの中心です。

### 素朴な文字列比較は使えない

```sql
-- abjp                              -- abus
SELECT o.id, o.amount                SELECT o.id, o.amount
FROM  mart_abjp.orders_abjp AS o     FROM  mart_abus.orders_abus AS o
WHERE o.region = 'abjp'              WHERE o.region = 'abus'
```

文字列としては 3 か所違いますが、**ロジックとしては同じ**です。素朴に diff を取ると
全 9 本が全部違って見え、何も分かりません。

### α 等価で判定する

SQL をトークンに分解し、**違っている箇所が一貫した 1 対 1 対応になっているか**を見ます。

```
トークン数が同じ ＋ 種類の並びが同じ ＋ 差が全単射  →  同じロジック
```

上の例なら `mart_abjp ↔ mart_abus` / `orders_abjp ↔ orders_abus` /
`'abjp' ↔ 'abus'` が一貫しているので **同じ**。一方こちらは：

```sql
-- abjp                              -- cdjp
WHERE o.status = 'CONFIRMED'         WHERE o.status = 'CONFIRMED'
                                       AND o.deleted_at IS NULL   ← トークン数が違う
```

トークン数が違うので **別グループ**。これが本物のロジック差です。

> **置換してよいのは「SQL の外を指す名前」と「値」だけ**にしてあります。
> 列名・別名・CTE 名・予約語が違えば、それは環境差ではなく書き換えなので、
> 差として残します。

差分表示では、グループ内で違っていた箇所を `{{P1}}` のように置き換えてから
比べます。だから**グループ間の比較にはロジックの差だけが残ります**。
何を置き換えたかはカードの末尾に一覧で出るので、判定の当否は人が確認できます。

### 何を「差」とみなすかは設定で選べる

**既定では、値（文字列・数値）もパラメータ化します。** つまり
`status = 'CONFIRMED'` と `status = 'DRAFT'` は**同じグループ**になり、
ロジック差分には出ません。末尾のパラメータ一覧に
`{{P3}} … abjp = 'CONFIRMED' / abus = 'DRAFT'` として並びます。

| SQL の違い | 既定 | `substitutable: ["entity"]` にしたとき |
|---|---|---|
| `FROM t_abjp` ↔ `t_abus`（参照先） | 同じグループ | 同じグループ |
| `status = 'A'` ↔ `'B'`（値） | **同じグループ**（パラメータ一覧に出る） | **別グループ**（差分に出る） |
| 列名・別名・CTE 名・構造 | 別グループ | 別グループ |

切り替えは `analyze_options` に 1 行足すだけです（UDF の作り直しは要りません）。

> **厳しくするときの注意。** 値を差として扱うと、`src = 'load_abjp'` のような
> **suffix 入りのリテラル**でも割れます。これは環境差なので、比較の直前に
> **その View 自身の suffix を伏せ字にする**仕組み（既定 on）が吸収します。
> `'apac' / 'amer' / 'emea'` のように suffix と綴りが違う対応語は、
> `equivalentLiterals` に組で並べて同値扱いにできます。

**どちらが正しいということはありません。** 値の差を「環境ごとの設定」とみなすなら
既定のまま、「レビューすべき差」とみなすなら切り替える。運用に合わせて決める設定です。

## 5. 構成

```
BigQuery                                   Looker Studio
┌──────────────────────────────────┐        ┌──────────────────┐
│ INFORMATION_SCHEMA               │        │ Templated Record │
│  SCHEMATA / VIEWS / COLUMNS      │        │  ＋ base のプルダウン │
│  COLUMN_FIELD_PATHS              │        └────────▲─────────┘
│  TABLE_OPTIONS                   │                 │ HTML を読むだけ
│            ↓ 日次のスケジュールドクエリ │                 │
│  JS UDF（解析・描画）              │                 │
│            ↓                     │                 │
│  t_diff_src  素のカード            │                 │
│  vw_t_diff   ＋ 運用メモ（その場で反映）│                 │
│  t_diff      焼き込み済み ───────────────────────────┘
└──────────────────────────────────┘
              ▲
   スプレッドシート（運用メモ・任意）
```

### 押さえておきたい設計

- **重い処理は日次に寄せてある。** 解析も HTML の組み立ても BigQuery の中で 1 日 1 回。
  レポートは出来上がった文字列を表示するだけなので速いです。
- **表示に JavaScript を使っていません。** Looker Studio のコミュニティ
  ビジュアライゼーションでは JS が動かないため、タブはすべて
  ラジオボタン ＋ CSS だけで実現しています。
- **運用メモだけはリアルタイム。** スプレッドシートを直すと、カードを作り直さなくても
  反映できます（メモを差し込む処理だけを流し直す）。
- **読み取り専用。** 対象の View やテーブルには一切書き込みません。

## 6. 導入に必要なもの

| | 内容 |
|---|---|
| BigQuery | データセット 1 つ（テーブル 3・ビュー 1・UDF 7 を置く） |
| スケジュールドクエリ | 1 本（日次） |
| Looker Studio | Templated Record のコミュニティ ビジュアライゼーション、データソース 1 つ |
| 権限 | 対象データセットの**読み取り**。メモを使うなら Drive の権限 |
| スプレッドシート | 任意（運用メモを使う場合のみ） |

設定は SQL 冒頭の `DECLARE` を書き換えるだけで、対象データセット・View 名の
絞り込み・suffix の拾い方をそこで指定します。**コードを読む必要はありません。**

読むのは `INFORMATION_SCHEMA`（メタデータ）と、対象 View の定義テキストだけです。
実データはスキャンしません。日次 1 回なので、走る量としてはごく小さい部類です。

### 導入時に決めること（運用）

環境をそろえれば動きますが、**運用として決めておきたいことが 3 つ**あります。

**(1) View / カラムの description をどう書くか（新規）**

いま、View にもカラムにも description を書く運用はありません。書かなくても
差分・カラム定義・参照関係・SQL は出ますが、**論理名や説明の欄は空のまま**です。

書く場合、置き場所は BigQuery のメタデータになります。**実物と同じ場所に置く
ので、デプロイと一緒に動き、実物から離れません。** カラムの description は
JSON で書けば日本語論理名と英語論理名を並べて表示できます。

  - 誰が、いつ書くか（新規作成時に必須にするか、既存は順次か）
  - どこまで書くか（全カラムか、主要なものだけか）
  - JSON のキーの綴りをそろえるか

**(2) 値（リテラル）の差をロジック差として扱うか**

既定では扱いません（4 章）。運用に合わせてどちらかを選びます。

**(3) Confluence と運用メモの棲み分け**

機械が持っている情報は自動で出せますが、背景・経緯・運用上の判断は人が書く
ものです。どちらに何を残すかを決めておきます。

## 7. 制約・注意（先にお伝えしておくもの）

- **Looker Studio のコミュニティ ビジュアライゼーション（Templated Record）が要ります。**
  組織のポリシーで使えない場合は、この形では出せません。
- **CSS はテンプレートに手で貼ります。** カードは日次で作り直されるので、機能を
  足したときに「新しいカード ＋ 古い CSS」の状態が起こりえます。そのときは
  **カード自身が「CSS を貼り直してください」と表示する**ようにしてあります。
- **1 レコード = 1 base の HTML** です。グループが極端に多い base は、行が壊れない
  ように途中で打ち切り、打ち切ったことを画面に出します。
- **論理名（description）は、書く運用を始めるまで空欄です。** いま View にも
  カラムにも description を書く運用がないためです。差分・カラム定義・参照関係・
  SQL は書かなくても出ます（6 章）。
- **既定では、値（リテラル）の差をロジック差として扱いません。**
  `status = 'A'` と `'B'` は同じグループになり、末尾のパラメータ一覧に出ます。
  値の差も割れてほしいなら設定で切り替えられます（4 章・6 章）。
- **Confluence を完全に置き換えるものではありません。** 機械が持っている情報
  （列定義・参照先・SQL）は自動で出せますが、**背景や経緯、運用上の判断は
  人が書くもの**です。それは運用メモに残す想定です（6 章）。
- **判定は SQL のテキストが根拠**です。実行結果が同じかどうかは見ていません
  （逆に言えば、結果が同じでも書き方が違えば差として出ます）。

## 8. これから（バックログ）

- **カラムの description（論理名）を編集する仕組み** — いまは読むだけ。
  置き場所が View の定義そのものなので、運用メモと同じ作りにはできず、
  「どこを正とするか」を決めるところから
- **base × suffix のマトリクス** — どの base にどの suffix が揃っているかの一覧
- **運用メモのエディタ** — Markdown のプレビュー付きで書ける画面

---

## 付録: デモの流れ（5 分）

1. base の一覧をグループ数つきで出す → **ロジックが 2 通り以上ある base はこれ**
2. その base を選ぶ → **ロジック差分**タブ。どこが違うかを色で見る
   → 意図した差か、直し忘れかを判断する
3. **カラム定義**タブ → SQL は同じなのに型が違う列を見せる
4. **参照関係**タブ → どのテーブルを読んでいるか
5. **note** タブ → 論理的な説明と運用メモ
