# 提案品質の自動評価（Eval）

生成される提案は毎回文面が変わる創作物なので、厳密な文字列一致ではなく
**2軸**で品質を自動評価します。

| 軸 | 内容 | 実装 |
|---|---|---|
| ① ルールベース | title/body 非空、推奨商品IDの妥当性、期待商品を含むか等 | 決定論・無料 |
| ② LLM-as-judge | grounding / relevance / actionability を各1〜5で採点 | ADK の `LlmAgent`（構造化出力）を審査員に使用 |

各ケースは「ルール違反ゼロ」かつ「judge平均 ≥ 3.5」で **PASS**。全ケースPASSで終了コード0。

## 実行

```bash
./.venv/Scripts/python.exe eval/run_eval.py
```

⚠️ 実行時に **Gemini 課金**が発生します（各ケースで 生成＋審査 のLLM呼び出し）。

## ケース（`eval/run_eval.py` の `CASES`）

ダミーデータの状況に基づく「最低限含んでほしい商品」を期待値にしています。

| 顧客 | 状況 | 期待（いずれか含む） |
|---|---|---|
| C002 | 解約リスク高・90日休眠 | P700/P800/P500/P300（活用促進・維持系） |
| C005 | ストレージ上限に頻繁到達 | P300（容量追加） |
| C001 | 上限接近・問い合わせ増 | P300/P500/P800（容量・サポート・分析） |

## 読み方・注意

- **FAIL は「壊れている」ではなく「品質が基準に届かなかった」**という意味です。
  例: 90日休眠のC002に追加アドオンを並べる提案は、審査員が「まず活用再開が先」と低評価にすることがあります
  （＝評価が機能している証拠）。
- LLMは非決定的なので**スコアは実行ごとに変動**します。安定評価が必要なら
  `AgentEvaluator`（`num_runs` で複数回平均）や、しきい値・ケース数の調整を検討してください。
- しきい値は `run_eval.py` の `JUDGE_PASS_AVG` で変更できます。

## 発展（ADK 標準の `adk eval` を使う場合）

ADK には EvalSet ベースの正式評価（`AgentEvaluator.evaluate` / `adk eval`）もあります。
ツール使用の軌跡（trajectory）を厳密に評価したい場合はそちらが向きます。
本ハーネスは「創作物の品質」をLLM-as-judgeで測ることに主眼を置いた簡易版です。
