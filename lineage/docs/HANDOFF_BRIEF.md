## 1. これは何か

BigQuery の SQL を解析して「**出力列 ← 物理テーブル.物理列**」の依存関係（カラムレベル
リネージ）を導出し、リポジトリに蓄積するシステムです。

- 解析エンジンは **JavaScript**（`javascript/src/`）。BigQuery の**永続 JS UDF** として動く
- パイプラインは **BigQuery スクリプト**（`sql/`）。View と INFORMATION_SCHEMA.JOBS の両方から
  SQL を集めて解析し、依存グラフを publish する
- レポートは Looker Studio（`looker/`、`docs/LOOKER_STUDIO_DESIGN.md`）

### 対象オブジェクトの 2 種類

| 種別 | 同一性のキー | 例 |
|---|---|---|
| **永続** | 宛先テーブル名 | View、実在するテーブルへの CTAS |
| **ephemeral** | **`sql_fingerprint`（SQL の構造指紋）** | 一時テーブル、期限付きテーブル、匿名結果 |

**ephemeral の挙動を理解することがこのプロジェクトの勘所**です。宛先が毎回変わるので、
名前では同一性を判定できず、SQL の構造で判定しています。

## 3. デプロイ手順

1. **バンドルを GCS に置く**（`javascript/dist/lineage_udf_bundle.js` を、01 の
   `bootstrap_udf_library_uri` が指す場所へ）
2. **`sql/setup/01_setup_lineage_environment.sql` を実行**
   - ⚠ **01 はリポジトリのテーブルを `CREATE OR REPLACE` します。既存データは消えます**
   - ビューだけ貼り直したいときは `recreate_views_only = TRUE`
3. **`sql/pipeline/03_run_daily_lineage_pipeline.sql` を実行**（これが日次バッチ）
4. 必要に応じて `sql/validation/04_validate_lineage_environment.sql` で健全性確認

**エンジン（`javascript/src/`）を変更したら**：再ビルド → 全テスト →
`release_manifest.json` の `sha256`/`size_bytes` 更新 → **GCS のバンドル差し替え**。
SQL 側の変更は不要です。

## 4. 主要パラメータ（03 の冒頭）

| 変数 | 現在値 | 意味と注意 |
|---|---|---|
| `initial_lookback_days` | 60 | **初回のみ**（job registry が空のとき）。収集と保持を兼ねる |
| `job_collection_lookback_days` | **3** | 2 回目以降の**収集**範囲の下限。実際の窓は「前回収集した最新 job 以降」まで自動延長される |
| `object_retention_days` | **40** | **ephemeral の保持期間**。8 で週次まで、40 で月次まで（31 日＋月末のずれ分の余裕） |
| `analysis_batch_max_sql_bytes` | **3,000,000** | バッチの大きさ。**バッチ数＝実行時間**なので最重要 |
| `analysis_batch_max_objects` | **3,000** | 同上。片方だけ上げても意味がない（`GREATEST(DIV(bytes,…), DIV(count,…))` で切るため） |
| `analysis_batch_group_datasets` | TRUE | バッチがデータセットをまたぐことを許可 |
| `analysis_max_batches_per_run` | 0（無制限） | 1 回の実行を区切りたいときに使う。やり残しは次回が続きから処理 |
| `analysis_skip_on_udf_resource_error` | TRUE | UDF の OOM でそのバッチだけスキップして継続 |
| `build_static_report_tables` | TRUE | レポート用ビューを物理テーブルにスナップショット |

### 収集の窓と保持の窓は別物（2026-10-06 に分離）

以前は 1 つの値が両方を決めていましたが、**それぞれ最適な長さが逆方向**なので分けました。

- **収集（`job_collection_lookback_days` = 3）は短いほどよい**。前回より古い job は
  すでに registry にあるので、再度 INFORMATION_SCHEMA から読む意味がありません。
  ただし**固定の短い窓は危険**（止まっていた期間の job を永久に取りこぼす）なので、
  実際の窓は registry の `MAX(creation_time)` から自動延長されます。普段は 3 日、
  1 週間止まっていれば自動で 8 日になります。
- **保持（`object_retention_days` = 40）は「載せたい周期」で決める**。ephemeral は
  指紋がこの窓の中で再出現し続ける限り active で、出なくなると `is_active = FALSE` に
  なり**依存行も削除**されます。月次ジョブを常時載せるには 31 日＋余裕が必要で、
  30 だと月末のずれで外れるため 40。

保持窓は age-out だけでなく、**MERGE の入力（`latest_generated_table_definitions`）の
絞り込みにも使われます**。registry は収集した job を保持し続けるので、絞らないと
「これまでに収集した全指紋」を毎回 MERGE することになります。

## 5. 今回のセッションでやったこと（要約）

**初期ロードが 2.5 時間で完走しなかった状態から、11 分 22 秒まで短縮しました。**

効いた順に:

1. **指紋を「識別子内の 6 桁以上の数字」に鈍感にした**（エンジン変更）
   → ephemeral の解析対象 SQL が 70% 減
2. **バッチ予算を 200,000 → 3,000,000 に**
   → バッチ数が実行時間そのもの。1 ステートメント約 1.5〜3 秒（大半はジョブ起動待ち）
3. **バッチがデータセットをまたげるように**
   → View 1 本のデータセット 58 個が 1 バッチに収まる
4. **ループ内の SQL レンダリングをループ外へ**、マーカー削減、INSERT 統合
   → 1 バッチ 42 → 30 ステートメント

あわせて**正確性のバグを 2 件**直しました（速度とは無関係）:

- **非アクティブから復活したオブジェクトが再解析されない**（週次 SQL の lineage が
  永久に欠損する）→ 両方の registry MERGE の `is_changed` に `OR target.is_active = FALSE`
- **リポジトリのテーブルが消えていても 03 が黙って作り直していた**
  → 冒頭の PREFLIGHT で名前を挙げて停止するように変更

## 6. 設計判断とその根拠（**ここが一番重要**）

### 6.1 指紋の数字畳み込みは「6 桁以上」。1〜2 桁は畳まない

**判断の根拠は「その値が使い捨てか、名前か」**です。桁数そのものではありません。

job 履歴 8 日分で、識別子内の数字列を「同じ値が何日出るか」で調べました:

| 桁 | 種類 | 1 日しか出ない割合 | 平均出現日数 | 判定 |
|---|---|---|---|---|
| 1 | 10 | 0% | 7.30 | **名前の一部** |
| 2 | 61 | 0% | 6.82 | **名前の一部** |
| 6 | 3,026 | 100% | 1.00 | 使い捨て |
| 8 | 6 | 100% | 1.00 | 使い捨て |
| 9 | 7 | 0% | 8.00 | 安定（巻き込まれるが 7 種類のみ） |
| 18〜20 | 8,572 | 100% | 1.00 | 使い捨て |

そして**実物で確認したところ、1 桁の数字の正体は CTE 名の `lvl_1` / `lvl_2`** でした。
階層レベルが違えば読むデータも違うので、**畳めば片方の lineage が消えます**。
1 桁から畳んでいたら階層を混ぜていました。

> **この境界を動かすときは、必ず `sql/maintenance/13_sql_pattern_drift.sql` の
> レポート 5 で「実際に違っている数字」を見てから決めてください。**

### 6.2 publish のまとめ込みは見送った

「バッチごとの publish を最後に 1 回にまとめれば速くなる」案は、**効果 9 分 → 実測後の
再計算で 1 分未満**と判明し、かつ「途中で止めると全部失われる」という代償があるため
**採用しませんでした**（現状は完了したバッチが即確定するので、キャンセルしても続きから）。

### 6.3 ephemeral を「古いものも残す」案は却下

解析回数は生涯 1 回で済みますが、実測の到着レート（当時 1,200〜1,350 指紋/日）だと
**1 年で約 45 万オブジェクト**に膨らみ、STEP 3 ではなく **STEP 4（impact 再構築）と
static テーブルが際限なく重くなる**ためです。

## 7. 診断ツールの使い分け

| スクリプト | 答える問い |
|---|---|
| `10_pending_analysis_workload.sql` | 次の実行は何件処理するか（1〜3）／滞留はどれだけか（4）／日次の新規発生数は（5・7）／指紋は再利用されているか（6）／数字は使い捨てか名前か（8）／**新規オブジェクトの実物はどれか**（9）／**次の実行が解析する一覧**（10） |
| `11_analysis_batch_diagnostics.sql` | バッチごとの所要時間（1）／失敗したステートメント（2）／**時間はどこに消えたか**（3・4）／**同じ形が何回流れたか**（5） |
| `12_ephemeral_sql_similarity.sql` | 指紋をもっと緩めたら何件畳めるか、それは安全か（1〜3）／数字の正体は（4・5）／ルール別の比較（6） |
| `13_sql_pattern_drift.sql` | **どのモデルの SQL が毎日変わっているか**（0〜3）／**今日の新規に畳む余地はあるか**（4）／**違っている数字は何か**（5・6） |

すべて読み取り専用です。`11` は実行単位に自動で絞り込みます（`REPORT_SCOPE` 行で確認）。

### 性能を調べるときの定石

1. `11` のレポート 4 で**フェーズ別の時間**を見る
2. `11` のレポート 5 で**同じ形が何回流れたか**を見る（**回数順**。時間順だと
   「1 本 0.1 秒を 100 回」が沈んで見えない）
3. `elapsed_sec` と `total_slot_ms` を**並べて**見る
   - elapsed はあるが slot が小さい → **起動待ち。ステートメント数を減らすしかない**
   - slot が大きい → 本当に処理している。クエリとして最適化する価値がある

## 8. 未了事項

### 8.1 ERROR 診断 17 件の確認（優先度: 中）

初期ロード時に `error_diagnostic_count = 17` が出ています。中身は未確認です。

- `lnge_t_diagnostic` を `diagnostic_code` 別に集計（`UDF_RESOURCE_ERROR` とそれ以外の切り分け）
- `lnge_t_unanalyzed_definition` の `coverage_reason` 別件数

### 8.2 JOBS 収集窓と保持窓の分離（優先度: 低、効果 約 30 秒/日）

日次 4 分のうち、**毎回 8 日分の JOBS を走査・MERGE している**のが 40 秒前後です。
ところが保持の判定は job registry（手元のテーブル）を見れば済むので、
**収集は「前回収集以降」だけで十分**です。

```
収集窓 = max(2日, 前回収集からの経過日数 + 余裕)   ← 新設
保持窓 = incremental_lookback_days（8 日、変更なし）
```

**着手する前に `11` のレポート 3・4 を日次実行に対して流し、内訳を実測してください。**
上記の 40 秒は初期ロード時の測定からの推定です。

### 8.3 日次運用の開始

スケジュール設定と、初回数日の監視ポイント:

- `resource_skipped_batch_count` が 0 か（0 でなければ OOM。予算を下げる）
- `remaining_changed_object_count` が増え続けていないか（増え続けるなら解析が失敗し続けている）
- `error_diagnostic_count` の推移

## 9. 守るべきルール

1. **識別子の匿名化を維持**。実プロジェクト名・データセット名はコードに書かない
   （`project_id` / `dataset` を使う）。**自社環境を特定させないためのセキュリティ方針**です
   - 同じ理由で**リポジトリ名・ブランチ名・ホスティング先も書かない**。この一式は別
     プロジェクトへ移して使うため、環境固有の名前が残ると移行先で混乱する。ファイル名・
     ディレクトリ名も同様（版数由来の `lineage_v<version>` は環境固有ではないので可）
2. **1 変更 = 実装 ＋ 番号付き回帰テスト ＋ CHANGELOG 追記**。
   テストは `javascript/test/test_v1_5_0_0XX.js` を新規作成し、`package.json` の
   `test:release` チェーンの**先頭**に追加（現在の最新は 080）
3. **エンジンを変えたらバンドル再ビルド → `release_manifest.json` 更新 → GCS 差し替え**
   - **UDF の署名を変えるときは `javascript/scripts/lib/deployment_udf_sql.js` を直す**。
     01 setup・再配備ヘルパ・03 の呼び出しが同じ署名を使っているので、どれかを忘れると
     `test_v1_5_0_080` が落ちる。経緯は `docs/UDF_DEPLOYMENT_CONSISTENCY.md`
4. SQL の `__T_*__` プレースホルダは `lnge_render_dynamic_sql` で解決する。
   修飾名はバッククォートで囲む（チームの規約）

## 10. BigQuery の落とし穴（このプロジェクトで実際に踏んだもの）

| 落とし穴 | 対処 |
|---|---|
| **ブロック自身の DECLARE は、そのブロックの EXCEPTION 節から見えない** | ハンドラが使う変数は 1 つ上のスコープで宣言する |
| `GROUPS` は予約語（ウィンドウフレーム）。CTE 名に使えない | 別名にする。エラーは `Invalid EXECUTE IMMEDIATE` としか出ないので気づきにくい |
| `ASSERT` の説明文は**文字列リテラルのみ**。変数を埋め込めない | 動的なメッセージが要るときは `RAISE USING MESSAGE = FORMAT(...)` |
| `EXECUTE IMMEDIATE ... USING` で**使われない名前付きパラメータ**を渡すとエラー | テンプレートと USING の対応を機械的に検査する |
| `JOIN ... USING (col)` の後にテーブル別名で同じ列を参照すると壊れることがある | 明示的な `ON` を使う |
| `diagnostic_json` は JSON 型。`TO_JSON_STRING` は STRING を返すので挿入できない | `JSON_OBJECT(...)` を使う |
| `ARRAY_AGG(DISTINCT <struct>)` 不可。ARRAY は ARRAY を含められない | STRUCT で包む |
| Looker Studio は ARRAY を読めない | 文字列化した列を併設する |
| スクリプトはトランザクションではない。**キャンセルしても完了済みは確定** | 冪等性と「続きから」を前提に設計する |
| RE2 に先読み・後読みは無い | 文字クラスと非捕捉グループで書く |
| `FORMAT` の中のリテラル `%` は `%%` | テンプレートの `%` を機械的に数えて検査する |
| **1 ステートメント ≒ 1.5〜3 秒（中身に関係なく）** | **速度はステートメント数で決まる**。ループ内の処理を減らすより、ループの回数を減らす |

## 11. 進め方について（このプロジェクトで繰り返し効いたこと）

**集計値は「どれだけ畳めるか」しか答えません。「畳んでよいか」は値そのものを見るまで
決まりません。**

このセッションでは、私（アシスタント）が集計値だけで 3 回結論を出し、3 回とも
利用者の指摘で覆りました。

1. 「4 と 6 の結果が一致＝頑健」→ 一致は「効いている桁が 6〜7 桁」を意味するだけだった
2. 「6 桁は日付ではない＝商品コード」→ 商品コードとは限らなかった
3. 「1 日しか出ない＝使い捨ての ID」→ **毎日違う商品コードを処理するジョブでも同じ**になる

最終的に正解に辿り着いたのは、**実際の値を見た**とき（`lvl_1` / `lvl_2`）でした。

`12` と `13` のレポートは、この教訓から「**余地を測るが、取るべきとは言わない**」
（measures the opportunity, does not propose taking it）という建て付けにしてあります。
