# 導入手順

何もない状態から、Looker Studio でカードが見られる状態までの順路。

- **仕組みと設定の意味** → `README.md`
- **レポートの読み方** → `usage.md`
- **導入の背景と効果** → `introduction.md`

> **貼る順番が効きます。** デプロイに shell を使わず、生成物を BigQuery の
> コンソールに手で貼る前提です。順番を違えると「関数が見つからない」
> 「引数の数が合わない」で落ちます。各段で何を見て OK とするかを書いてあるので、
> 上から順に進めてください。

---

## 0. 用意するもの

### 権限

| 対象 | 要るもの |
|---|---|
| 解析対象のデータセット | **読み取り**（`INFORMATION_SCHEMA` と View 定義しか読みません。実データはスキャンしません） |
| 置き場所のデータセット（`work_dataset` / `udf_dataset`） | テーブル・ビュー・ルーチンの作成 |
| 運用メモを使う場合 | スプレッドシートへの Drive 権限（BigQuery の外部テーブルとして読みます） |

スケジュールドクエリは**その実行者の権限で動く**ので、登録する人が上を満たして
いるか確認してください。

### データセット

置き場所が 1 つあれば足ります（既定は `ops_meta`）。テーブル用と UDF 用を分けたい
なら 2 つ。**解析対象と同じリージョンに作ること。**

### Looker Studio

**Templated Record** というコミュニティ ビジュアライゼーションを使います。
ギャラリー掲載品で公開元がホストしているので、**こちらで GCS バケットを公開する
必要はありません**。組織ポリシーでコミュニティ ビジュアライゼーションが
許可されている必要があります。

### 手元（生成するとき）

`view_group_html.sql` と `template_style.html` は生成物です。**配布されたものを
そのまま貼るなら不要**ですが、作り直すなら Node.js と esbuild が要ります。

```bash
cd view_logic/ddl_diff_viz && npm install   # esbuild が入る
cd ../view_groups && node build_udf.mjs        # 2 つを作り直す
```

## 1. 設定を決める

書き換えるのは `DECLARE` だけです。**コードを読む必要はありません。**

### まず見る 5 つ

| | 場所 | 何を入れるか |
|---|---|---|
| `SET @@location` | 両ファイルの先頭 | 解析対象のリージョン（例 `asia-northeast1`）。**`DECLARE` より前にある唯一の設定** |
| `work_dataset` | `build_table.sql` | テーブルとビューの置き場所 |
| `udf_dataset` | **両ファイル** | UDF の置き場所 |
| `analysis_include_dataset_patterns` | `build_table.sql` | どのデータセットの View を集めるか（既定は末尾 4 文字の suffix を持つもの） |
| `note_sheet_url` | `build_table.sql` | 運用メモのスプレッドシート URL。**使わないなら空のまま** |

### 両ファイルで必ず同じ値にする 4 つ

`view_group_html.sql` と `build_table.sql` の両方にあります。**食い違うと
`build_table.sql` が関数を見つけられません。**

```
system_name       既定 'viewlgc'
udf_dataset       既定 'ops_meta'
udf_name_prefix   既定 ''
udf_name_suffix   既定 ''
```

既定値がそろっているかは `node check_sql.mjs` が突き合わせます。

> 残りの設定（suffix の拾い方・除外・基準の行数上限など）は既定のままで動きます。
> 意味と変えどころは `README.md` にあります。

## 2. 貼る

### ① `view_group_html.sql` → UDF を作る

BigQuery のコンソールにファイルの中身をそのまま貼って実行します。

**できるもの: ルーチン 12 本。**

| | |
|---|---|
| `viewlgc_analyze` | View 群を解析して JSON を返す（JavaScript） |
| `viewlgc_panes` | ロジック差分のペイン（左右の比較）を作る |
| `viewlgc_render` | そのペインを嵌めてタブと外枠を付ける |
| `viewlgc_erd` | 参照関係の図を作る |
| `viewlgc_page` | カラム定義と SQL を足し、外側タブで束ねる |
| `viewlgc_markdown` | 運用メモの Markdown を HTML にする |
| `viewlgc_group_css` | テンプレートに貼る CSS を返す |
| `viewlgc_render_dynamic_sql` | `build_table.sql` の `__…__` を展開する（SQL 関数） |
| `viewlgc_group_css_p1` 〜 `p4` | CSS の部品。`group_css` が連結する（1 本では 32 KB に収まらないため） |

**OK の判定**: 最後に 8 つの関数名と `created_at` が 1 行で出ます。
これを次の段に使うので、`system_name` / `udf_dataset` を変えたなら控えておきます。

### ② `build_table.sql` → テーブルとビューを作る

同じく中身をそのまま貼って実行します。**初回はファイル全体を 1 回流します。**

**できるもの:**

| 名前 | 何 | セクション |
|---|---|---|
| `viewlgc_m_base_note` | 運用メモの外部テーブル（スプレッドシート） | 1 ← **初回とシートを変えたときだけ** |
| `viewlgc_t_diff_src` | 素のカード（メモ差し込み前） | 2 |
| `viewlgc_vw_t_diff` | 素のカード ＋ メモ | 3 |
| `viewlgc_t_diff` | それを写したテーブル。**カードのレポートはこれを読む** | 3b |
| `viewlgc_vw_t_matrix` | base × suffix のマトリクス用ビュー | 3c |

**OK の判定**: セクション 5 の確認クエリが順に結果を返します。
**まず 5-1 を見て、base ごとに行が出ていれば通っています。**
サンプルを入れてあるなら `v_daily_sales / 9 View / 3 グループ` になります。

落ちたときは下の「6. 落ちたときに見るところ」へ。

### ③ `template_style.html` → Looker Studio のテンプレートに貼る

**カードは CSS を持っていません。** クラス名だけで書いてあり、CSS は
Templated Record のテンプレート側に 1 回貼ります。

`template_style.html`（生成物）の中身を `<style> … </style>` で囲んでテンプレートの
先頭に置き、その下に `diff_html` のフィールドを差し込みます。

> BigQuery から取ることもできます（中身は同じ）。
> `SELECT \`<project>.<udf_dataset>.viewlgc_group_css\`('{"mode": "class"}');`

**OK の判定**: カードに**色とタブが付く**こと。貼る前は素の HTML に見えます。

> **2 者比較の頃に配っていた CSS は使えません。** あちらは見出し・タブ・
> パラメータ表の `.vg-*` 規則を含まないため、貼ってもタブが動きません。
> 使うのは必ず `template_style.html`（または `viewlgc_group_css` の出力）です。

## 3. Looker Studio を配線する

ページを 2 枚作ります。**どちらも集計も加工もしません。**

### カードのページ

1. **データを追加 → BigQuery** で **`viewlgc_t_diff`** を選ぶ
   （テーブル選択でよい。カスタムクエリは不要）
2. **Templated Record** を配置し、表示対象のカラムに **`diff_html`** を指定
3. **コントロール → プルダウン リスト**を **2 つ**置く。どちらも
   **「単一選択にする」をオン**（Templated Record は 1 レコードしか描かない）

   | | フィールド | 何を選ぶか |
   |---|---|---|
   | 1 つ目 | `base` | どの View 群を見るか |
   | 2 つ目 | `ref_label` | どのグループを基準にするか |

4. **Templated Record の並べ替えを `ref_index` 昇順**にする

> **4 を忘れないこと。** グループは解析の時点でメンバの多い順に並んでいるので、
> `ref_index = 0` がいちばん View の多いグループです。昇順にしておけば
> **`ref_label` を選んでいない状態で多数派が基準になります。** 並べ替えが
> 既定のままだと、どの基準が出るか決まりません。

> **ビュー（`viewlgc_vw_t_diff`）を読ませないこと。** 開くたびに Drive を読み、
> JS UDF を回し、数 MB の文字列に `REPLACE` をかけるので遅くなります。
> `viewlgc_t_diff` は同じ内容を写したテーブルです。

### マトリクスのページ

1. **データを追加 → BigQuery** で **`viewlgc_vw_t_matrix`** を選ぶ
2. **ピボット テーブル**を配置する

| 置き場所 | 何を置くか |
|---|---|
| 行のディメンション | `base` |
| 列のディメンション | `location`、`suffix`（**この順**。上の段が `location`） |
| 指標 | `group_no`（集計は最大値） |

**OK の判定**: 同じ行で数字が割れている base があれば、そこがロジック差分です。

> **`t_diff` の配列（`suffixes` / `locations`）でこの表は作れません。** 対応が
> 添字にしかなく、レポート側に「この 2 本は組」と伝える手段がないためです。
> 詳しくは `README.md` の「base × suffix のマトリクス」。

## 4. スケジュールドクエリに登録する

`build_table.sql` の **CONFIGURATION ＋ セクション 2・3・3b・3c** を 1 本の
スケジュールドクエリとして登録します（日次）。

| セクション | 登録するか |
|---|---|
| CONFIGURATION | **する**（設定の `DECLARE`。これが無いと動かない） |
| 1（メモの置き場所） | しない。初回とシートを変えたときだけ手で流す |
| 2・3・3b | **する**（本体） |
| 3c（マトリクス用ビュー） | **してよい。** ビューなので 1 度作れば中身は 2 に追従しますが、入れておけばこのファイルを直したときに定義も作り直されます |
| 4（CSS） | しない。既定でコメントのまま |
| 5（確認） | しない。確認用 |

`INFORMATION_SCHEMA` の中身は View をデプロイしたときしか変わらないので、
日次で十分です。

> **リージョンをまたぐ場合は、取り込みを先に流すこと。**
> 詳しくは「9. リージョンを増やすとき」。

## 5. 動いていることを確かめる

`build_table.sql` のセクション 5 に確認クエリが並んでいます。**どの段で何を見るか。**

| 確認 | 何を見るか | 期待 |
|---|---|---|
| **5-1** | 生成結果の中身 | base ごとに行がある |
| **5-2** | ロジックが割れている base | 要確認の一覧。0 件でなくてよい |
| **5-3** | suffix を認識できなかった View | 少ないほどよい。多いなら suffix の拾い方を見直す |
| **5-3b** | **名前が重複する View** | **0 件であること。** 下の「8. 前提」を参照 |
| **5-4** | 実際に使う suffix の一覧 | 意図した suffix が並んでいるか。除外したものも理由付きで出る |
| **5-5** | データセット別の対象 View 数 | 集めるつもりのデータセットが並んでいるか |
| **5-5b** | View 名の条件で落ちた View | 落とすつもりのないものが混ざっていないか |
| **5-6** | 条件から外れたデータセット | 同上 |
| **5-7** | メモの登録状況 | **既定でコメントのまま**（ここだけ Drive を読むので遅い）。メモを直したときに外す |
| **5-8** | マトリクスの grain | `cells = views` / `duplicated_cells = 0` / `cells_without_group = 0` |
| **5-9** | suffix の切り出しが SQL と UDF で一致しているか | **0 件であること** |

**初回に必ず見るのは 5-1・5-3b・5-4・5-8・5-9** です。
5-3b と 5-9 は**0 件でなければ正しく扱えていません**。

## 6. 落ちたときに見るところ

`ASSERT` の文言から原因が引けるようにしてあります。よく当たるもの。

| 出る文言 | 原因と直し方 |
|---|---|
| `UDF が 8 つそろっていません` | ①を飛ばしたか、`system_name` / `udf_dataset` / `udf_name_prefix` / `udf_name_suffix` が両ファイルで違う |
| `対象の View が 0 件です` | `@@location` が違うか、`analysis_include_dataset_patterns` / `analysis_include_object_patterns` が絞り過ぎ |
| `suffix を持つデータセットが 0 件です` | データセット名から suffix が拾えていない。`suffix_list` に一覧を並べるか `suffix_extra_list` に足す |
| `プロジェクト ID を自動検出できません` | そのリージョンにデータセットが無い。`work_project_id` などにリテラルを入れて固定する |
| `work_dataset は英数字と _ だけに…` | `{project_token}` が置換されずに残っている |
| `note_sheet_url はスプレッドシートの URL…` | URL の形が違う。メモを使わないなら空にする |
| `運んできたメタデータが足りません` | リージョン間の取り込みが流れていない。文言に「探した値」と「実際にあった値」が出る |
| `… に未展開のプレースホルダが残っています` | `viewlgc_render_dynamic_sql` が古い。①を貼り直す |

**カードの上に「このカードには新しい CSS（世代 N）が要ります」と出る場合**は
落ちていません。③の貼り直しが要るだけです（下の 7）。

## 7. 直したときに貼り直すもの

| 直したもの | ① UDF | ② テーブル | ③ CSS |
|---|---|---|---|
| `build_table.sql` の設定だけ（suffix の拾い方・除外など） | — | **要** | — |
| `analyze.js` / `render_groups.js` など UDF の中身 | **要** | **要** | — |
| 見た目・CSS（`CSS_GEN` を上げた） | **要** | **要** | **要** |
| スプレッドシートのメモの内容 | — | 3b だけ流し直す | — |

> **`CSS_GEN` を上げたときは 3 つ全部やること。** 世代の番号は CSS だけでなく
> **カードの markup にも入ります**（`chrome.js` の `cssGuard()` が出し、UDF に
> 焼き込まれる）。**両方の番号が一致したときだけ案内が消えます。**
> 「見た目だけの変更だから UDF はそのままでよい」は誤りです。

UDF を作り直すときは、先に `node build_udf.mjs` で生成物を更新します。

## 8. リリース時の前提・既知の穴

出す前に確認しておきたいこと。

### 前提

- **View 名がリージョン内で一意であること。** base の切り出しは View 名だけで
  畳むので、**重複していると 1 本だけ採って残りが黙って消えます**（カラム定義も
  混ざる）。**確認クエリ 5-3b が 0 件であることが前提です。** 0 件でない状態が
  続くなら、データセットまで含めた識別に作りを変える必要があります（未対応）。
- **判定の根拠は SQL のテキスト**です。実行結果が同じかどうかは見ていません。
  結果が同じでも書き方が違えば差として出ます。
- **既定では値（リテラル）の差をロジック差として扱いません。** `status = 'A'` と
  `'B'` は同じグループになり、パラメータ一覧に出ます。設定で切り替えられます。

### 範囲外

- **論理名（description）は空欄のまま出ます。** 読む仕組みはできていますが、
  書く運用を始めていないためです。書き始めれば翌日のカードから出ます。
  このツールから description を**編集する**仕組みはありません。

### 画面の上限（超えたら必ず画面に出ます）

黙って消えるものはありません。すべて「全 N 件のうち先頭 M 件」と出します。

| 対象 | 上限 |
|---|---|
| ロジック差分のグループ タブ | 12 |
| SQL タブ（View 単位） | 128 |
| description の種類 | 16 |
| ラベルの種類 | 8 |
| 基準の行（`max_ref_rows`） | 24 |

### 次に触るとき知っておくこと

**UDF の本体は 1 個 32 KB まで**で、いまの余裕はこうです。

| 関数 | 最小化後 | 上限比 |
|---|---|---|
| `viewlgc_analyze` | 11.1 KB | 37% |
| `viewlgc_panes` | 13.3 KB | 44% |
| `viewlgc_render` | 15.8 KB | 53% |
| `viewlgc_erd` | 20.1 KB | 67% |
| `viewlgc_page` | 21.6 KB | 72% |
| `viewlgc_markdown` | 6.5 KB | 22% |

現在値は `node build_udf.mjs` が毎回出し、**30 KB を超えたら生成が失敗します**
（BigQuery に弾かれるものを出荷しないため）。詰まってきたら依存が独立している
ところで UDF を割るか、`OPTIONS(library=["gs://…"])` に移します（BigQuery は
ジョブの認証情報で読むので**非公開バケットで構いません**）。

> `viewlgc_render` は 27.0 KB（90%）まで来ていたので、差分エンジンを
> `viewlgc_panes` に切り出して 15.8 KB（53%）にしました。**出力は
> バイト単位で変わっていません。**

## 9. リージョンを増やすとき（任意）

拠点 1 リージョンだけで足りるなら**この節は不要**です。

別リージョンの View も同じカードに混ぜたい場合、**メタデータを運びます**
（BigQuery は 1 ジョブ = 1 ロケーションで、`INFORMATION_SCHEMA` をまたいで
読めないため）。

リージョンを 1 つ増やすたびに要るもの:

| 場所 | 増えるもの |
|---|---|
| 送り元のリージョン | GCS バケット 1 ＋ データセット 1 ＋ スケジュールドクエリ 1（`cross_region_export.sql`） |
| 拠点 | `cross_region_import.sql` の `sources` に 1 行、`build_table.sql` の `import_sources` に 1 行 |

**拠点側のジョブは増えません**（`sources` が配列なので取り込み 1 本で全送り元を
捌きます）。N リージョンでスケジュールドクエリは **N＋2 本**（export N ＋ import 1
＋ build 1）。

実行順は **export（各送り元）→ import（拠点）→ build（拠点）**。手順の詳細と
命名のそろえ方は `README.md` の「複数リージョンの View をまとめて解析する」。

> **送り元が止まったことに気づく人が要ります。** 運んだメタデータが
> `max_staleness_hours`（既定 36 時間）を超えたら取り込みが落ちる作りですが、
> **落ちたことを見る人がいないと、拠点だけ古いままで動き続けます。**

## 10. 試す・片付ける

### サンプルで試す

BigQuery に実データを作って通しで確かめられます。

```bash
node build_sample_sql.mjs   # sample_data.sql / sample_teardown.sql を生成
```

`sample_data.sql` の `PROJECT` を置換して流すと、データセット 4 つ・
ソース テーブル 18 本・View 9 本ができます。期待する結果は
**`v_daily_sales` / 9 View / 3 グループ**（`[abjp, abuk, abus]` `[cdjp, cduk, cdus]`
`[efjp, efuk, efus]`）。

### 片付ける

`sample_teardown.sql` が**データセットごと**消します。`PROJECT` を置換し、
**他の用途と同居させていないか確認してから**流してください。

### 戻し方

生成するテーブルは**毎回まるごと作り直す**（`CREATE OR REPLACE TABLE … AS SELECT`）
ので、**落ちたときは前日の内容がそのまま残ります。** 欠けたカードで上書きされる
ことはありません。設定を戻してもう 1 度流せば元に戻ります。

履歴は持っていません。**常に最新の 1 世代だけ**です。
